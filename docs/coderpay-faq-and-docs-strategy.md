# CoderPay FAQ 与文档治理草案

> 状态：草案，待确认后再接入官网或控制台。  
> 目标：沉淀一份面向开发者的常见问题说明，并明确官网文档与控制台接口文档的调整方向。

## 一、CoderPay FAQ 草案

### 1. CoderPay 是什么？

CoderPay 是面向个人开发者和小团队的微信、支付宝个人收款自动化工具。开发者上传自己的微信或支付宝收款码，用户付款后资金直接进入开发者个人账户；CoderPay 负责订单创建、收款码调度、Android 到账监听、订单匹配、手续费扣除和 Webhook 回调。

### 2. 用户付款的钱会经过 CoderPay 吗？

不会。普通开发者订单的资金直接进入开发者自己的微信或支付宝账户，CoderPay 不代收、不托管、不清算用户支付资金。

平台订阅充值是另一条链路：开发者给 CoderPay 账户充值技术服务余额时，资金进入平台配置的收款账户，用于支付套餐或每笔交易手续费。

### 3. 微信可以像支付宝一样一键唤起 App 完成支付吗？

不能稳定做到。微信个人收款码没有公开稳定的浏览器直达个人转账能力。  

微信支付在微信内置浏览器中通常可以长按二维码识别，或由用户保存二维码后在微信扫一扫中识别。CoderPay 会保留微信二维码兜底，不承诺微信个人码一键直达。

### 4. 支付宝可以一键唤起并自动带入金额吗？

可以，但前提是开发者配置了支付宝 PID，也就是支付宝收款账户的 `2088...` 用户 ID。  

配置 PID 后，CoderPay 可以在手机端生成支付宝转账链接，打开支付宝并带入本次订单的精确金额。若只有支付宝二维码内容，没有 PID，通常只能唤起支付宝识别收款码，金额仍需要用户核对或手动输入。

### 5. 为什么要安装 Android App？

CoderPay 的核心原理是监听微信、支付宝的到账通知。Android App 安装在开发者自己的收款手机上，用于读取系统通知栏里的到账金额，并把到账事件安全上报给 CoderPay 云端，云端再匹配订单并触发回调。

### 6. 收款手机需要 root 吗？

不需要。CoderPay 通过 Android 系统通知读取权限工作，不需要 root，也不需要修改微信或支付宝 App。

### 7. 收款手机必须一直在线吗？

如果希望订单自动确认、自动回调，收款手机需要保持在线，并且通知读取权限、微信/支付宝通知、后台保活都正常。

如果手机没电、没网或通知被系统拦截，用户付款后 CoderPay 无法实时收到到账通知，订单不会自动成功。当前系统支持人工确认模式：开发者可以在控制台核对实际到账后点击“我已收款”，系统会扣除手续费、标记订单成功，并触发商户回调。

### 8. 手机离线时还能创建订单吗？

普通开发者订单可以。只要开发者有可用的 active 收款码，手机离线时订单会进入人工确认模式，用户仍可付款，开发者需要在控制台核对到账后人工确认。

平台订阅充值更严格：平台收款设备需要在线后才允许创建充值单，避免平台自营收款出现大量人工对账风险。

### 9. 订单未支付成功会扣手续费吗？

不会。只有订单被自动匹配成功，或开发者在控制台人工确认“我已收款”后，系统才会扣除每笔交易手续费。

如果订单一直未支付、已过期或被用户取消，不扣手续费。

### 10. 用户已经付款，但开发者没有收到回调，可能是什么原因？

常见原因包括：

- 收款手机离线、没电、断网或 Android App 未运行。
- 未开启通知读取权限。
- 微信或支付宝没有在通知栏展示到账金额。
- 手机系统把微信、支付宝或 CoderPay 的通知静默、折叠或拦截。
- 用户在订单过期后才付款。
- 商户 Webhook 接口超时、报错，或没有返回纯文本 `success`。
- 同一金额存在多笔候选订单，系统进入人工审核，避免误回调。

遇到这种情况，开发者应先在控制台查看订单、到账事件、异常和回调日志，再根据实际到账进行人工确认或重推回调。

### 11. 支付二维码过期后用户仍然付款，怎么办？

过期订单不会自动成功回调。开发者可以在控制台订单管理中找到对应订单，核对到账记录后点击“我已收款”，CoderPay 会把订单标记为成功并触发回调。

如果是平台订阅充值单过期后付款，应由平台管理员在管理后台核对后使用“人工确认充值到账”，不要直接改数据库。

### 12. CoderPay 稳定吗？会不会掉单？

CoderPay 已实现设备心跳、到账事件幂等、订单金额微调、同金额冲突拦截、异常记录、人工确认和回调重试等机制，目标是降低漏单和误单风险。

但个人收款码免签方案依赖手机通知、微信/支付宝通知展示和 Android 后台保活，运营稳定性与手机环境强相关。上线前必须完成真机小额闭环测试，并建议准备长期插电、网络稳定的专用备用机。

### 13. 微信收到款后通知栏没有金额怎么办？

需要开启微信收款到账语音提醒和通知详情。通常路径是：微信“我” -> “服务/钱包” -> “收付款” -> “二维码收款” -> 右上角菜单 -> 开启收款到账语音提醒。

同时需要在手机系统通知设置中允许微信显示通知详情。如果通知只显示“收到一条消息”，CoderPay 无法解析到账金额。

### 14. 支持支付宝官方收钱码吗？

支持。CoderPay 支持支付宝普通个人收款码和官方收钱码。为了获得更好的手机端支付体验，建议同时填写支付宝 PID，使支付宝付款页可以带入精确金额。

### 15. 支持企业微信买单二维码吗？

可以作为后续兼容项评估。第一阶段以微信个人收款码、支付宝个人收款码和支付宝官方收钱码为主。企业微信买单码需要做真实通知样本采集后再确认解析规则。

### 16. 可以自定义支付页面吗？

当前推荐使用 CoderPay 托管收银台 `/pay/checkout`。后续可以提供 JSON 模式，让开发者自己渲染付款页，但仍建议由 CoderPay 返回订单状态、真实应付金额、二维码能力和过期时间，避免开发者错误处理金额微调和过期状态。

### 17. CoderPay 如何扣费？

套餐费用需要开发者提前订阅或续费。每笔订单手续费从开发者的 CoderPay 技术服务余额中扣除。

余额低于预警线时控制台会提示充值；余额不足时，自动确认或人工确认可能会被拦截，开发者需要先充值余额。

### 18. 技术服务余额的用途是什么？

技术服务余额仅用于套餐订阅和每笔交易手续费，不作为现金账户；异常退款、特殊结算或大客户处理需联系平台人工审核。

### 19. CoderPay 有收款限额吗？

不同套餐有不同的单笔订单上限。专业版支持更高单笔收款上限，高级版支持更高阶的运营能力。实际支付还会受到微信、支付宝个人账户自身风控和限额影响。

### 20. 上传收款二维码数量有限制吗？

第一阶段不做高频批量上传承诺。建议开发者按真实收款场景上传少量稳定可用的通用码或固定金额码。大批量码池、企业级导入和更复杂调度可以作为后续高级能力。

### 21. 固定金额收款码可以自动识别吗？

CoderPay 会尝试从二维码 payload 中确定性解析常见金额参数，例如 `amount`、`money`、`total_amount`、`total_fee`。如果能识别，会辅助切换为固定金额并预填金额。

如果二维码内容不包含金额，CoderPay 不做 OCR 猜测，避免误识别造成订单匹配失败。开发者需要手动选择通用码或固定金额码，并核对金额。

### 22. 月流水高可以免套餐费吗？

可作为运营政策保留：例如 30 天流水超过指定阈值后，由平台人工审核后赠送或延长高级版权益。第一阶段不建议承诺“自动免套餐费”，除非后台对账、风控和自动发放规则已经完全闭环。

### 23. 使用个人微信或支付宝收款有风险吗？

有平台规则风险。CoderPay 的技术链路与普通二维码收款一致，资金也直接进入开发者账户；但个人收款码用于商业化收款仍可能受到微信、支付宝账户规则、频率、金额、投诉和风控影响。

建议开发者合理使用，避免异常高频、虚假交易、灰产内容和高投诉业务。

### 24. CoderPay 是否适合大规模公开运营？

适合从受控小范围真实订单试运营开始，逐步扩容。大规模公开运营前，需要完成 WAF 限流、自动备份、设备离线告警、Webhook 自动补偿、日对账报表和真机长稳测试。

## 二、官网文档与控制台接口文档如何调整

### 推荐结论

可以合并为“一份接口规范，两种展示入口”。

- 公开官网 `/docs`：讲清楚原理、接入流程、FAQ、限制和风险，保留必要 API 说明，但不要放过多“复制即可运行”的完整工程级 SDK。
- 控制台“接口文档”：使用同一份接口规范数据，但结合当前登录开发者的 App ID、回调地址、沙箱订单和接入体检，强调“按你的配置联调”。

### 当前代码状态

当前公开文档和控制台文档已经在使用共享的 `lib/docs/api-spec.ts`，这是正确方向。后续应继续把以下内容集中维护：

- API endpoint、method、字段说明。
- 请求和响应示例。
- 签名规则。
- Webhook 回调 payload。
- 状态枚举。
- 错误码。

展示层只负责不同场景渲染：

- `/docs` 面向未登录访客和新开发者。
- `/console` 的接口文档面向已登录开发者，自动带入 App ID、沙箱参数、接入体检和 Webhook Ping。

### 建议的信息架构

公开官网文档：

1. 系统总览：资金直达、Android 监听、订单匹配、Webhook。
2. 快速接入：注册、创建应用、上传收款码、绑定设备、创建订单。
3. 支付体验说明：支付宝直达条件、微信二维码兜底、过期订单处理。
4. API 概览：创建订单、查询订单、Webhook。
5. 签名规则：只讲必要规则。
6. FAQ：解释限制、风险和人工确认。
7. 联系支持。

控制台接口文档：

1. 当前应用选择器。
2. 复制当前 App ID。
3. App Secret 显示、重置和安全提示。
4. 沙箱创建订单。
5. 接入体检。
6. Webhook Ping。
7. 语言示例，建议只保留短示例，不提供完整可复制平台实现。
8. 错误排查：设备离线、余额不足、无收款码、回调失败。

## 三、关于“避免开发者照文档复制出同类支付平台”的现实判断

### 先说结论

不能依靠隐藏文档来防止模仿。个人收款码 + Android 通知监听 + 云端匹配这个大方向不是秘密，开发者把文档丢给模型后，模型可以复刻一个粗糙版本。

真正能形成壁垒的是：稳定性、运营数据、调度策略、异常处理、风控、设备端体验、自动补偿、对账、客服和长期迭代，而不是把接口文档写得模糊。

文档过度隐藏反而会伤害正常开发者接入，降低转化率。

### 不建议做的事

- 不建议把基础 API 做成“故意难懂”。
- 不建议依赖前端混淆、加密 JavaScript、隐藏字段来保护商业模式。
- 不建议要求开发者安装闭源 SDK 才能创建订单，除非你的目标客户愿意接受强绑定。
- 不建议把签名算法设计成复杂但无安全收益的私有算法，这会增加接入成本和售后负担。

### 建议做的防模仿与产品壁垒

#### 1. 接口安全层：标准、安全、不过度暴露内部机制

公开文档只暴露商户必须知道的内容：

- 创建订单。
- 查询订单。
- Webhook 回调。
- 签名校验。
- 状态枚举。

不要公开：

- Android 到账通知解析正则。
- 金额微调和二维码调度细节。
- 同金额冲突判定规则。
- 设备健康评分算法。
- 异常匹配规则。
- 平台充值内部流程。
- 管理后台接口。

#### 2. 增加“服务端签发订单票据”机制

可以在创建订单成功后返回一个短时有效的 `checkout_token`，收银台和状态轮询必须带这个 token。这样别人即使知道订单 ID，也无法随意轮询或嵌入你的收银台。

作用：

- 防止订单 ID 被枚举。
- 防止支付页被第三方批量抓取。
- 增加平台侧订单控制能力。

#### 3. App Secret 只显示一次，支持轮换

控制台创建应用时只显示一次 App Secret，之后只允许重置。文档里强调：

- Secret 只能放在开发者服务端。
- 不允许放前端。
- 泄露后必须重置。

这属于基本安全，不是防抄袭，但能降低滥用。

#### 4. Webhook 增加时间戳与 nonce

Webhook payload 建议增加：

- `timestamp`
- `nonce`
- `signature_version`

开发者服务端校验时间窗口和 nonce 去重。这样接口更专业，也减少被伪造回调的风险。

#### 5. 订单创建增加时间戳签名

创建订单请求也可以增加：

- `timestamp`
- `nonce`
- `sign_version`

服务端拒绝超时请求，并记录 nonce 防重放。这样比“私有加密算法”更可靠。

#### 6. 收银台能力由服务端动态下发

不要让文档教开发者自己拼全部支付逻辑。应让 `/api/order/create` 返回：

- `payment_url`
- `checkout_token`
- `expires_at`
- `real_amount`
- `confirm_mode`
- `channel_online`

开发者只需要跳转到 CoderPay 收银台。二维码调度、支付宝直达、微信兜底、过期判断、轮询提示都由 CoderPay 控制。

#### 7. Android 端增加设备签名与版本门槛

当前已有设备签名基础，可以继续加强：

- 每台设备独立 secret。
- 请求时间戳。
- nonce 防重放。
- App 版本检查。
- 低版本 App 限制使用。
- 设备心跳健康评分。

这部分不写进公开文档，只在系统内部实现。

#### 8. 把核心竞争力放在运营闭环

优先做这些比“隐藏文档”更有效：

- Webhook 自动补偿队列。
- 设备离线告警。
- 每日对账报表。
- 异常订单归因。
- 安卓通知样本库。
- 厂商保活引导。
- 多设备调度策略。
- 订单人工确认审计。
- 管理后台运营工具。

### 文档公开边界建议

可以公开：

- 产品原理的高层说明。
- 商户接入 API。
- 签名校验规则。
- Webhook 回调格式。
- Android 安装和权限配置。
- 常见问题。
- 风险说明。

不公开：

- 管理后台地址。
- 管理后台接口。
- 平台充值账号细节。
- 内部异常类型完整规则。
- 到账通知解析细节。
- 金额尾差算法细节。
- 二维码调度算法。
- 设备签名内部协议。
- 数据库结构。
- 部署方式和 Cloudflare 配置细节。

## 四、建议的后续执行任务

### P0：先整理文档，不改逻辑

1. 确认本 FAQ 文案。
2. 把 FAQ 接入 `/docs`，但不要放进控制台导航。
3. 把公开文档里的夸张表述收敛，例如“绝对安全”“无一漏单”等，改成更稳健的“资金直达”“降低漏单风险”“支持人工确认补单”。
4. 控制台接口文档继续保留联调能力，不把管理后台或内部机制暴露出去。

### P1：统一接口规范源

1. 扩展 `lib/docs/api-spec.ts`，补齐字段表、错误码、状态枚举、FAQ 引用。
2. 公开文档和控制台文档都从同一份 spec 渲染。
3. 控制台文档只增加登录态相关能力，例如真实 App ID、沙箱订单、Webhook Ping。

### P2：增强接口安全

1. 订单创建增加 `timestamp`、`nonce`、`sign_version`。
2. Webhook 增加 `timestamp`、`nonce`、`signature_version`。
3. 收银台增加 `checkout_token`。
4. 后端记录 nonce，限制重放。
5. 文档中保留标准签名说明，但不公开内部反作弊规则。

### P3：形成真正壁垒

1. Webhook 自动重试队列。
2. 设备离线告警。
3. 日对账。
4. Android 长稳测试与厂商保活指南。
